# Retained financial approval and Ledger mapping

The optional owner composition is off by default. Native posting and financial approval must both be enabled explicitly. Apply the separately delegated optional V10 and V11 migrations before enabling the financial approval store. V1-V9 remain unchanged. V11 preserves unbound V10 history; a prior unbound approval cannot acquire a mapping later or authorize Ledger source observation.

The maker proposes the full immutable mapping together with the complete original posting. Core persists the proposal, its independent snapshot SHA, its owner-assigned snapshot UUID, the original mapping-definition reference, and its original completed audit link on the same owner root. The independent checker approves that exact retained proposal using current policy and a different issuer/subject and canonical staff identity. The retained `gl_native_mapping.definition_digest` continues to mean the SHA of its original definition; it is never reinterpreted as the new snapshot SHA.

## HTTP lifecycle

The protected base path is `/api/v1/tenants/{tenantId}/books/{bookId}/financial-approvals/{approvalId}`. POST requests the full proposal, POST `/check` independently approves it, POST `/revoke` revokes it, and GET returns the currently authorized complete retained proposal for independent checker review. The detail includes the exact original posting JSON, typed posting, full mapping, owner-assigned snapshot ID and SHA, intent digest, business lifetime and retained approval state. A state-only response is insufficient for checker review. Request bodies contain stable command IDs and the complete versioned business proposal. They contain no actor, token, permission, or approval authority. The current native security context supplies identity. The request operation retains the exact embedded `originalPosting` object bytes, including its formatting. Keep these bytes, the approval ID, command IDs, original action ID, and intent stable across recovery.

The check command must echo the reviewed snapshot ID, snapshot SHA and intent digest along with its stable command ID and expected revision. Core compares these references against the genuine immutable retained binding before approval and before replay. Stale snapshot IDs, changed mapping digests or changed intent digests cannot approve or replay a check.

The proposal is not a grant. A successful approval response is not a financial posting. Unavailable responses require observation with the original identities; they never authorize allocating a replacement action. The durable approval lifetime is independent from the original command/JWT limit, which remains at most five seconds.

## Full mapping and genuine source observation

The `GL_LEDGER_MAPPING_SNAPSHOT_V1` encoding includes the original mapping reference, both Ledger account/enrollment/contract IDs, both same-book liability posting leaves, each complete ordered control path and its versions, the full Ledger/Masters currency crosswalk, and the exact Core currency admission and version. Core stores the complete canonical body rather than a client digest alone. Current owner checks require active exact book/account/control/currency metadata. The new native admission gate locks the current approval and ordered control ancestors after the original native gate, then rechecks finite authority after waits.

The optional Ledger observer uses the genuine generated `LedgerFundsApi.getFundsMonetaryReceipts(tenant, reservationId, null)`. It validates the retained typed monetary envelopes and their canonical digests, exact source IDs, exact occurrence, account/enrollment/contract crosswalk, and the two liability-transfer lines. Its outgoing decoded and signature-validated JWT must have the configured issuer, subject, audience, client, machine kind and tenant, `funds:read`, and actual `funds_accounts` grants for both Ledger account UUIDs. Requested client scopes or resources do not substitute for issuer grants. HTTP is allowed only for an explicitly enabled literal loopback test endpoint; production profiles require HTTPS.

Set `firefly.accounting.ledger-source.enabled=true` only with explicit tenant-bound profiles and genuine OAuth client registrations, current policy and owner approval composition. There is no approving fallback. Local source controls and the Core approval/snapshot fixture do not establish a genuine Ledger transport or a Domain/Experience financial journey.
