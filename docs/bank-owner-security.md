# Bank owner observation security

The GL web application uses the shared reactive JWT resource server, OAuth2 client configuration, and OPA adapter. HTTP authorization defaults to strict policy enforcement with no public route exceptions. Adding a client registration does not enable a login page or OAuth2 login redirect. Configure the trusted issuer, JWKS endpoint, audience, tenant projection, and current application policy before serving protected requests.

Bank owner observation remains disabled unless explicitly enabled. The `bank-owner-observation` profile supplies the standard client-credentials registration and the exact organization owner profile. Its settings are in `core-common-accounting-gl-web/src/main/resources/application-bank-owner-observation.yaml`. Supply every required `GL_AUTH_*`, `GL_OWNER_*`, and `GL_BANK_OWNER_POLICY_*` setting through deployment configuration. `GL_OWNER_CLIENT_SECRET` has no fallback. Blank or unresolved credentials for a selected native registration fail startup without including the credential in the error.

The incoming GL caller and outgoing organization observer have separate issuer, audience, tenant, and identity settings. A cached OAuth client name is not machine authority. The observer validates the server-issued JWT, fetches the exact current owner through the generated organization SDK, and checks current caller policy before and after the read. Its original wall-clock and monotonic limits remain in force through response emission.

The default OPA backend requires an explicit decision path and an HTTPS endpoint; a numeric loopback HTTP endpoint is supported for a local sidecar. No permissive policy is installed. An application-provided policy backend, security chain, or OAuth registration and client manager remains selected. Custom registration stores remain responsible for their own configuration and continue through the observer's existing runtime identity checks.

This capability observes institution and enrollment metadata. It does not approve an accounting book, grant a license, admit financial activity, post money, or establish regulatory compliance. The book approval and native posting paths require their own real owner integrations. A new original application and SDK qualification is required after dependency changes; earlier artifacts do not acquire this security wiring automatically. Qualification with a framework source reactor also does not establish availability of equivalent released dependencies.
